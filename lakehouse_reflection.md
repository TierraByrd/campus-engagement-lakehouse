# Lakehouse Architecture Reflection

The folder layout in this project follows the same pattern real lakehouses use on cloud storage like S3. Each month of data sits in its own folder named year=2024/month=09, and the query engine reads those folder names as columns. That's what makes partition pruning work. When I ran the October query with EXPLAIN, DuckDB showed it scanned 1 of 3 files and skipped the rest. With three small CSVs that doesn't save much, but in a real system with years of LMS logs, skipping every folder you don't need is the difference between reading a few files and reading millions of rows. The files are also stored raw, with no load step. DuckDB applies the structure when it reads them, which is schema-on-read.

The metadata files are what keep this from becoming a data swamp. Without them, the November file showing up with a seventh column would be a mystery. Nobody would know whether delivery_mode was new, a mistake, or something that was supposed to be in every file. The YAML spells out what columns exist, what values are allowed, which version the table is on, and what kinds of changes are allowed. A real lakehouse goes further with ACID transactions, which this project doesn't have. Here, if a file got cut off halfway through being written, DuckDB would read the partial file anyway and the numbers would be wrong. Delta Lake and Iceberg avoid that by keeping a transaction log, so a new file only counts once its entry is written to the log. Readers see the whole change or none of it, and two people writing at the same time can't corrupt the table.

Open table formats like Delta, Iceberg, and Hudi matter because they add those rules without locking the data inside one product. The data stays as regular files that Spark, Trino, Python, or DuckDB can all read. A traditional warehouse works differently. I'd have to define the table first and load the data in before I could query anything, which is schema-on-write. The data would live in the warehouse's own storage, and only that warehouse could query it. Adding delivery_mode would mean altering the table inside the warehouse instead of just writing new files under a new metadata version. The warehouse gives you speed and strict structure out of the box. The lakehouse gets close to that while keeping storage cheap and open.
